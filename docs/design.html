Design note

AI Oversight: three-stage extraction pipeline

ai_oversight turns an AI-governance report (PDF or PPTX) into 22 canonical fields defined by PLAN.md — submission ID, model owner, risk rating, and so on — each with a value, a citation back to the source document, a status, and a confidence score. The pipeline runs in three stages, and the second and third each only do real work when the cheaper stage before them couldn't finish the job.

The organizing rule throughout is never fabricate: a value is only ever reported as confidently extracted when it can be traced to real text in the source document. Every other outcome — needs_review, ambiguous, conflicting, missing — exists so that uncertainty is visible to a human reviewer instead of silently guessed away.

The pipeline, end to end

Stage 1 is always cheap and deterministic. Stage 2 (Granite Vision) only runs on the specific pages/slides Stage 1 flagged as ambiguous — a vector-drawn chart, a scanned page, or a picture shape — never on content Stage 1 already parsed cleanly. Stage 3 maps whatever elements exist (native + vision-recovered) onto the 22 canonical fields, using either a fast deterministic backend or a two-pass local LLM backend.

Dashed outlines/edges mark the two conditional branches: Stage 2 only runs for flagged pages, and the second qwen_local pass only runs for fields the main pass left missing.

Stage 1 — Structural parse

pdf_parser.parse() (PyMuPDF) and pptx_parser.parse() (python-pptx) turn the raw file into the shared intermediate representation: a flat list of Elements, each one text, key_value, table, or chart. No model runs here — everything is regex, geometry, and shape structure.

PDF specifics

Column-aware text blocks (the source reports are two-column); label→value pairing gated by on-page distance so a pairing is never guessed across unrelated text; a vector-drawn chart's gridline cluster is detected and its bounding region computed for Stage 2 to crop later.

PPTX specifics

Numbered-ID shape rows become key_value elements; non-ID multi-shape rows become table elements (ambiguous, multi-cell); a picture shape is never silently dropped — it's recorded as a warning that routes it to Stage 2.

This stage also decides, implicitly, whether Stage 2 has anything to do: a page that parsed cleanly carries no warning and is never sent to the vision model.

Stage 2 — Granite Vision (conditional)

granite_vision.run_vision_pass() only fires for exactly three situations Stage 1 could flag but not resolve on its own:

TriggerTask sent to GraniteWhy
A page has a vector-drawn chart (gridlines detected, not a native chart object)chart2csvPyMuPDF can see the strokes but not what they encode
A PDF page has no text layer and contains an image (fully scanned page)tables_jsonno native content exists to fall back on
A PPTX picture shapetables_jsoncan't tell chart from table from a bare image, so the more general task is the default

Granite's raw response is repaired if the model's EOS token cut it off mid-table (_repair_truncated_json recovers every complete row before the cutoff), then merged back into the IR as ordinary Elements — a recovered chart becomes a chart element, a single clean instance row becomes a key_value, and a genuinely multi-instance table stays a cautioned table element. Whichever Stage 3 backend runs next never knows the difference between native and vision-recovered content.

Because this stage is slow (a real local vision model), its output can be cached once with the vision CLI command and replayed via extract --vision-cache — Stage 3 can then be iterated on repeatedly without re-running Granite.

Stage 3 — Field mapping

Two interchangeable backends consume the same IR and produce the same ExtractionResult shape.

rules backend — deterministic

Matches each key_value/table element's own numbered field_id or label text against the canonical 22, with a synonym table for common wording variants. No model, no network, effectively instant — the right choice when the source document's own numbering is reliable.

qwen_local backend — two-pass local LLM

Runs Qwen3-4B-Instruct-2507 locally (greedy decoding — more on why below) in two passes:

① Main pass — chunked, multi-field

_chunk_by_page → _build_prompt → _extract_chunk → _build_evidence → _resolve_field_candidates

Each page is split into groups of at most 5 elements (MAX_ELEMENTS_PER_CHUNK) — asking a 4B model to match ~15 candidates against 22 fields in one call measurably hurt recall. Each chunk's prompt lists every canonical field's own PLAN.md description (not just its name) and warns that a table-type element describes one repeated instance, never the whole document. Every citation is checked against its source element's actual text before counting as substantiated, and a citation from a table-type element is always unsubstantiated — a structural rule, not a prompt request, because the model can choose to ignore a prompt instruction but can't bypass a code-level check.

② Second pass — per field, whole page

_second_pass_missing_fields → _build_single_field_prompt → _extract_single_field

For whatever fields are still missing after the main pass, ask about exactly one field at a time against the entire page's elements (no further sub-chunking — a single-field prompt has no multi-field output budget to protect). This pass's prompt also invites a tentative citation from a table-type element instead of forbidding it outright, since the structural check above already guarantees it can never outrank a verified answer — it can only ever surface as needs_review.

Both passes resolve candidates through the same merge rule: candidates are only ever compared for conflict within a confidence tier. A verified citation always wins over a disagreeing unverifiable one; a low-confidence table guess can never drag a correctly-substantiated answer down to conflicting.

Confidence score

Every field carries a confidence float — a triage signal for a reviewer, not a literal probability. It's a Pydantic computed_field on FieldValue, derived purely from status and evidence, so it can never drift out of sync with either one.

StatusBandMoves toward ceiling when…
conflicting0.15 – 0.29fewer disagreeing sources (more sources disagreeing is a worse sign)
ambiguous0.30 – 0.44more independent evidence flagging the same field as present-but-unclear
needs_review0.45 – 0.70more independent citations agreeing on the same unverified value
extracted0.85 – 1.00more independent, verified citations agreeing on the same value
missing0.00— no value, nothing to be confident about

The bands never touch, so a needs_review field — no matter how much corroborating evidence it has — can never out-rank even a weakly-supported extracted one.

floor, ceiling = band for this status if status == "conflicting": # more disagreement = worse, so corroboration runs backward corroboration = max(SATURATION_CONFUSED - evidence_count, 0) / (SATURATION_CONFUSED - 2) else: corroboration = max(0, min(evidence_count - 1, SATURATION - 1) / (SATURATION - 1)) confidence = floor + (ceiling - floor) * corroboration

Worked example: human_oversight extracted from 3 independently-agreeing, verified citations lands at the top of the extracted band — 1.00. The same field with just one citation would sit at the band's floor, 0.85.

CLI commands

ai_oversight parse <file> --out ir.json

Stage 1 only. No model. Useful for inspecting what the structural parser alone found.

ai_oversight vision <file> --out cache.json

Stage 2 only, saved to disk. Run once; reuse below as many times as needed.

ai_oversight extract <file> --backend qwen_local --vision-cache cache.json --out result.json

The full pipeline, Stage 3 reading from a saved vision cache instead of re-running Granite. Writes result.json and result.review.md. Drop --vision-cache and add --vision to run Granite live instead; drop both to skip Stage 2 entirely.
